# QuizForge — 設計と実装の記録

授業資料から試験問題を自動生成し、解答から採点・復習までを一貫して扱う Web アプリ。
この文書は「何をどう作ったか」、特に **LLM の出力をどう信用しないか** の設計判断を残したもの。

---

## 1. つくった動機

試験勉強でやっていたことは、だいたい次の 3 段だった。

1. 授業スライドや配布 PDF を読み返す
2. 「たぶんここが出る」と当たりを付ける
3. 手を動かさないまま、読んだだけで理解した気になる

問題は 3 に集約される。読むのは受動的で、思い出せるかどうかが検証されない。
自分に問題を出してくれる相手がいれば解決するが、その相手を用意するコストが高い。
市販の問題集は「自分の授業で配られた資料」には対応しない。

**手元の資料そのものから、解ける形の問題が出てくればいい。** それが出発点。

---

## 2. できること

| 項目 | 内容 |
|---|---|
| 入力 | PDF / Word / Excel / HTML / テキスト / 画像（PNG・JPEG・GIF・WebP） |
| 出題形式 | 5択（正解1つ）・複数選択（正解2〜4つ、部分点）・記述・穴埋め |
| 難易度 | 易 / 標準 / 難 を比率で指定。出題範囲や観点も自由記述で指定できる |
| 採点 | 選択は自動、記述は AI が部分点、穴埋めは表記ゆれを吸収して照合 |
| 復習 | 間違えた問題だけを再出題。AI が解説を生成（一度作ったら再課金しない） |
| 整理 | フォルダー分け、問題単位の削除と差し替え |
| 運用 | 複数ユーザー、グループ配布、プラン制限、利用量とコストの管理画面 |

**テキスト抽出の前処理を持たない。** 資料のファイルをそのまま Bedrock へ渡している。
図やスキャン PDF も、モデルが画像として読める範囲で扱える。

## 3. 全体構成

```
ブラウザ (React + Vite / PWA)
        │  fetch + セッションクッキー
        ▼
Cloudflare Tunnel ── HTTPS で公開
        │
        ▼
Express (TypeScript)
   │      └ 同一オリジンで web/dist も配信 → CORS 設定が不要になる
   ├── 認証 / プラン制限 / 検証層
   ├── 非同期ジョブワーカー
   │
   ├──► PostgreSQL（16 テーブル）
   └──► Amazon Bedrock  Converse API
             ├ 作問  Claude Sonnet 5  ← 資料を直接読む
             ├ 採点  GLM-5            ← テキストのみ・安価
             └ 解説  GLM-5
```

サーバー PC 上で `server/dist/local.js` を常駐させ、Cloudflare Tunnel 経由で公開している。
`start.cmd` がソースの更新を検出して、必要なときだけビルドしてから起動する。

## 4. 技術スタックと選定理由

| 層 | 採用 | 理由 |
|---|---|---|
| 言語 | TypeScript 5.8.3 | フロントとサーバで型定義を共有したかった |
| フロント | React 18.3.1 + Vite 6.3.5 | ビルドが速い。PWA 化はプラグインで済む |
| サーバ | Express 4.21.2 | ミドルウェアで認証を 1 か所に寄せられる |
| DB | PostgreSQL（pg 8.16） | `jsonb` で設定を持ちつつ、集計は SQL に任せられる |
| 検証 | Zod 3.25 | 利用者の入力と**モデルの出力**を同じ書き方で検証できる |
| AI | Amazon Bedrock Converse API | モデルを差し替えても呼び出し側を変えずに済む |

フロントの実行時依存は `react` と `react-dom` の 2 つだけ。
UI ライブラリを入れず CSS を自分で書いた。画面数が少なく、
デザインの統一より「読みやすさ」を優先したかったため。

## 5. 設計の起点 — LLM に任せないことを先に決めた

LLM に丸投げすると、**毎回違う失敗をする**ものができあがる。
再現しないバグは直せないので、責務を先に線引きした。

| モデルに任せる | コードが決める・検証する |
|---|---|
| 資料を読んで問題文をつくる | 何をいくつ出すか（形式 × 難易度の内訳） |
| 誤答の候補を考える | 選択肢の並び順 |
| 記述解答の妥当性を判断する | 点数の正規化と合否の閾値 |
| 解説の文章 | 出力が仕様を満たしているかの検査 |

**「文章を書く仕事」だけを渡し、数と構造はコードで押さえる。**
以下はこの線引きをどう実装したかの記録。

## 6. 実装の詳細

### 6.1 出題構成をサーバで確定させる

`plan.ts`

「5択 60% / 記述 20% / 穴埋め 20% で 25 問」をモデルに計算させると、
合計が 24 問や 26 問になる。割合の計算は LLM がもっとも雑になる部分だった。

そこで**最大剰余法**で整数配分してから、確定した内訳を文章にしてプロンプトへ渡す。

```ts
const floors = shares.map((s) => Math.floor(s));
let remaining = total - floors.reduce((a, b) => a + b, 0);
// 小数部が大きい順に 1 ずつ配る → 合計は必ず total に一致する
const order = shares
  .map((s, i) => ({ i, frac: s - Math.floor(s) }))
  .sort((a, b) => b.frac - a.frac || a.i - b.i);
```

形式で配分 → 各形式の中を難易度で再配分、の 2 段。
モデルに見せるのは「5択・易 3問、5択・標準 5問…」という確定した表だけ。

### 6.2 構造化出力を強制する

`bedrock.ts` `converseForJson`

自由文で JSON を書かせると壊れる。Converse API の **tool use** を使い、
JSON Schema を宣言して `toolChoice` でツール呼び出しを強制した。

ただしモデルによって受け付けない指定がある。`temperature` を拒否するモデル、
`toolChoice` の強制を受け付けないモデルがそれぞれ存在した。
拒否された要素を外して再試行し、**判明した制約はモデル単位で記憶する**。

```ts
if (withTemperature && /temperature/i.test(message)) {
  NO_TEMPERATURE_MODELS.add(modelId);   // 次回以降は最初から付けない
  withTemperature = false;
  continue;
}
if (forceTool && /toolChoice|tool_choice/i.test(message)) {
  NO_TOOL_CHOICE_MODELS.add(modelId);   // auto にフォールバック
  forceTool = false;
  continue;
}
```

出力がトークン上限で切れた場合は、「構造化出力を返さなかった」という曖昧な失敗にせず、
`stopReason === 'max_tokens'` を検出して原因を明示するエラーに変換している。

### 6.3 モデル出力を信用しない検証層

`quiz.ts` `normalizeQuestion` / `cloze.ts` `isValidCloze`

スキーマを宣言しても、内容が問題として成立するとは限らない。
1 問ずつ検査して、**成立しない問題は捨てる**。

- 5択：選択肢がちょうど 5 件、重複なし、正解インデックスが 0〜4
- 複数選択：正解が 2〜4 件、重複なし、5 件すべて正解は不可
- 穴埋め：`{{1}}{{2}}…` が 1 から始まる連番で、`blanks` と個数・順序が一致
- 記述：模範解答が存在する

```ts
if (!isValidCloze(raw.question, blanks))
  return drop(`空欄マーカーと解答の対応が取れない（解答${blanks.length}件）`);
```

捨てた理由はすべてログに残す。「なぜ 25 問頼んで 22 問なのか」を後から追えるようにするため。
不足分は **1 回だけ**追加生成して補う。何度も呼ぶとコストと所要時間が読めなくなる。

### 6.4 壊れた出力を復元する

`quiz.ts` `repairSwallowedObject` / `parseIfJsonString`

運用して見つかった実際の壊れ方。モデルがあるキーの値に、後続のキーまで巻き込んで
文字列化してしまう。

```json
{ "questions": "[{...},{...}],\"title\":\"三角関数の基礎\"}" }
```

`questions` が配列にならず、しかも**巻き込まれた `title` が失われる**。
これは「生成が失敗する」と「クイズ名が汎用の文言になる」という、
一見別々に見えた 2 つの不具合の共通原因だった。

キー名を付け直して再パースすれば元に戻る。

```ts
const restored = tryParseJson(`{${JSON.stringify(key)}:${trimmed}`);
// → {"questions":[...],"title":"三角関数の基礎"} として復元できる
```

このほかに用意した復元経路。

- 文字列リテラル内の生の改行やタブをエスケープし直して再パースする
- コードフェンス（json 付きの三連バッククォート）で囲まれている場合は外す
- **途中で切れた配列から、完結している要素だけを拾う**

1 文字壊れただけで全滅していた状態から、部分成功で返せるようになった。
それでも解釈できなかった場合は、Zod のエラー詳細をそのまま利用者に見せず、
日本語のメッセージに置き換えて 502 を返す。診断用のログには出力の「形」と先頭だけを残し、
資料の中身は記録しない。

### 6.5 非同期ジョブ — 100 秒の壁

`jobs.ts`

25 問の生成には実測で **約 70 秒**かかる。Cloudflare の応答タイムアウトは 100 秒。
同期で返す設計は成立しない。

受付だけして **202 Accepted** を返し、処理は後ろで走らせる。

```ts
await query('INSERT INTO jobs (id, user_id, kind, payload) VALUES ($1,$2,$3,$4)', ...);
setImmediate(() => { void runJob(id).catch(...); });  // 応答を待たせない
```

二重実行の防止は **DB の条件付き UPDATE** で行う。

```sql
UPDATE jobs SET status = 'running', started_at = now()
  WHERE id = $1 AND status = 'queued'
  RETURNING user_id, payload
```

`queued` を `running` に**変えられた側だけ**が処理へ進む。行が返らなければ何もしない。
アプリ側でロックを持たないので、プロセスが増えても壊れない。

落ちたときの扱い。

- **再読み込みで進捗に戻れる** — 未完了ジョブを一覧できるので、ページを閉じても生成は続く
- **起動時の復帰** — `running` のまま残った孤児は実行主体がいないので失敗にし、`queued` は拾い直す
- **payload を捨てる** — 資料の base64 を含んで重いので、終了時に `'{}'` で上書きする
- **7 日で削除** — ジョブは履歴として残す価値がない
- **失敗したら枠を消費しない** — `usage_log` に書かないので、作成回数の上限が減らない

最後の 1 点は方針として通した。失敗の責任が利用者にない場合に枠を減らすのは筋が悪い。

### 6.6 正解位置の偏りを潰す

`quiz.ts` `shuffleChoices`

LLM に選択肢を作らせると、**正解が A や B に偏る**。慣れると内容を読まずに当てられてしまい、
問題としての価値が落ちる。

プロンプトで「散らして」と頼むのではなく、サーバ側で Fisher-Yates シャッフルし、
正解インデックスを付け替える。

```ts
const { choices: shuffled, order } = shuffleChoices(choices);
return {
  choices: shuffled,
  answerIndex: order.indexOf(answerIndex),   // 並べ替え後の位置へ写す
};
```

複数選択も同様に正解インデックスの集合を写し、昇順に整えてから保存する。

### 6.7 採点 — 形式ごとに手段を変える

**記述**（`grade.ts`）は AI に任せる。ただし出力は構造化して受け取り、閾値はコードで決める。

- 0〜100 点の部分点。採点観点（`keyPoints`）を何個満たしたかで判定する
- 80 点以上を `correct`、40〜79 を `partial`、39 以下を `incorrect`
- 表現の違い・語順・同義語では減点しない、と明示する

**穴埋め**（`cloze.ts`）は AI を使わない。文字列照合だが、そのままでは厳しすぎる。

```ts
value.normalize('NFKC')       // 全角/半角を統一
     .toLowerCase()
     .replace(/\s+/gu, '')
     .replace(/[「」『』“”"'（）()、。,.・:：;；!！?？]/gu, '');
```

ここで重要なのは、**意味が変わる差を正規化で潰さないこと**。
送り仮名の違いや漢字とかなの違いは、正規化ではなく
「許容表記をモデルに複数列挙させ、先頭を代表表記とする」方針に分けた。
正規化で吸収しすぎると、別の語を正解にしてしまう。

空欄が複数ある問題は、空欄ごとの正誤から 0〜100 に正規化する。
空欄が 4 個ある問題と 1 個の問題で、点数の意味が変わらないようにするため。

### 6.8 モデルを役割で分ける

`modelConfig.ts`

3 つの用途は要求が違うので、同じモデルを使う理由がない。

| 役割 | 必要な能力 | 採用 |
|---|---|---|
| 作問 | PDF・画像を**直接読む** | Claude Sonnet 5 |
| 採点 | テキスト処理 + 構造化出力 | GLM-5（安価） |
| 解説 | テキスト処理のみ | GLM-5（安価） |

管理画面から切り替えられ、DB の値が環境変数より優先される。
ただし**候補は `.env` の `BEDROCK_MODEL_CHOICES` に列挙したものだけ**に限定した。

Bedrock には 150 近いモデルがある。全部から選ばせると、作問に使えない
テキスト専用モデルを指定して壊す事故が起きる。運用者が確認したものだけを候補にした。

コストは `model_prices` テーブルにモデルごとの単価を持ち、
**使用履歴の行ごとに計算して合算**する。単価の違うモデルを混ぜて平均しない。

Bedrock の制約への対応もいくつか入っている。

- document の name に使えるのは英数字・空白・ハイフン・括弧だけ。
  日本語ファイル名は渡せないので `material 1` に置き換え、
  対応表（`material 1 = 「〇〇.pdf」`）をプロンプト本文に書いて参照させる
- 1 ファイル 4.5MB が上限。プラン設定の最大値もこれに合わせた
- HTTP ボディは base64 で 4/3 に膨らむので、上限をプランの合計 MB より大きく取る

### 6.9 可用性 — 混雑で落ちないように

`bedrock.ts` `withResilience`

運用中に `us.anthropic.claude-sonnet-5` が **14 回中 12 回** `503` を返す事象に遭遇した。
モデル一覧の取得も認証も通るので、AWS 側のキャパシティ不足だと切り分けた。

対策は 3 段。

1. **接頭辞を変える** — `global.` は世界中の空きを使うので詰まりにくい（同一モデル・同一単価）
2. **粘る** — 一時的な失敗と判定できるものだけ 3 回まで。指数バックオフにジッタを足す
3. **逃げる** — それでも駄目なら代替モデルへ切り替える

```ts
// 403（権限不足）や 400（入力不正）は即座に投げる。
// 再試行で設定ミスを隠すと、原因の分からない遅い失敗になる。
if (!isTransient(error)) throw error;
```

**実際に応答したモデル ID を課金記録に書く。** 途中で切り替わってもコスト集計が実態と合う。

## 7. セキュリティ

`auth.ts`

| 対象 | 実装 |
|---|---|
| パスワード | `scrypt`、ソルト付きの `salt:hash` 形式 |
| セッション | 平文トークンは Cookie、**DB には SHA-256 ハッシュだけ**保存 |
| Cookie | `HttpOnly` / `SameSite=Lax` / `Secure` は転送ヘッダから自動判定 |
| 総当たり | IP 単位 **と** ユーザー名単位の二重で制限 |
| 存在漏洩 | ユーザーが居なくてもハッシュ検証と同等の時間をかける |
| 権限昇格 | 管理者は `.env` 固定。どの経路で作られるユーザーも `role = 'user'` |

Cookie の `Secure` を自動判定にしたのは、環境変数の付け忘れでセッションが平文で飛ぶのを
防ぐため。Cloudflare Tunnel はローカルへ http で転送してくるので、
`X-Forwarded-Proto` を信頼しないと「HTTPS なのに http 扱い」になる。

管理者アカウントを `.env` に固定したのは、管理画面から管理者を増やせる経路を作らないため。
管理画面のアカウント作成機能でも `role` は `user` に固定している。

使わなくなった Lambda ハンドラ（`lambda.ts`）は、削除せず **501 を返す状態で残した**。
認証を入れた時点でこのハンドラは Express のミドルウェアを通らなくなり、
公開すればログインなしで生成と採点を叩けてしまう。
危ないコードは「動かないことを理由付きで明示して残す」ほうが、
消して忘れるより安全だと判断した。

## 8. データモデル

16 テーブル。

```
users ── plans                 プラン制限（ファイル数・容量・出題数・作成回数）
  ├── sessions                 セッション（ハッシュのみ）
  ├── quizzes ── questions     クイズと問題
  │     └── attempts ── answers    挑戦と解答
  ├── folders                  整理
  ├── question_marks           復習マーク（要復習 / 完璧）
  ├── usage_log                トークン消費（課金の元データ）
  └── jobs                     非同期ジョブ

groups ── group_members ── shares    グループ配布
app_settings                          モデル設定
model_prices                          モデル別単価
```

スキーマの更新は「列を足す `ALTER` を `IF NOT EXISTS` で並べる」方針。
マイグレーションツールを入れず、起動時に冪等な DDL を流している。

設定値は `jsonb` で持ち、集計は SQL 側に寄せた。
コスト計算を SQL で書いたことで、ユーザー別・モデル別・日別を同じ式から出せている。

## 10. つまずいた順の記録

1. **割合がずれる** → 配分をサーバに移した（6.1）
2. **JSON が壊れる** → tool use で構造化を強制した（6.2）
3. **スキーマは通るのに問題として成立しない** → 検証層を足した（6.3）
4. **それでも壊れた形で返ってくる** → 復元処理を書いた（6.4）
5. **生成が長くてタイムアウトする** → 非同期ジョブにした（6.5）
6. **正解が偏る** → シャッフルをサーバに置いた（6.6）
7. **コストが読めない** → 役割ごとにモデルを分け、単価をモデル別にした（6.8）
8. **AWS 側が混雑して落ちる** → 再試行と代替モデルを入れた（6.9）

共通しているのは、**LLM の出力を「外部からの入力」として扱い、境界で必ず検査する**という一点。
ネットワーク越しのデータを検証するのと同じ扱いにすると、設計の見通しがよくなった。

---

## 11. 残っている課題

- **パスワード変更機能がない** — 管理者が発行した初期パスワードを本人が変更できない。
  `must_change_password` フラグと変更画面が必要
- **問題の質を評価できていない** — いまは「仕様を満たすか」しか見ていない。
  良問かどうかを測る手立てがない
- **穴埋めの表記ゆれ** — 許容表記の列挙をモデル任せにしている部分が残る
- **総当たり対策がプロセス内** — カウンタがメモリ上にあるので、複数台構成にするなら DB か Redis へ移す
- **自動テストがない** — 6.4 の復元処理のように、モデルの気分で壊れ方が変わる箇所は
  テストで固めたい。テストランナー自体をまだ入れていない
- **Lambda 構成** — `createApp()` を `serverless-http` で包み、
  RDS / Aurora への接続と接続プールの扱いを設計し直す必要がある
